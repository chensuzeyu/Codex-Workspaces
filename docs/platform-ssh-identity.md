# 平台托管公钥与个人身份

在共享 Linux 用户下，多个人的 SSH 公钥可对应不同 Codex profile；SSH 授权、个人身份路由、Codex 凭据和代理端口是不同层。它们不提供 Unix 用户级的权限隔离。

## 当前公开版支持什么

本项目的 `ssh install` 为公钥写入 `environment="CWS_SSH_PROFILE=..."`，dispatcher 读取该变量；可选 tmux 会传递该变量。安装器不会修改 sshd 或平台只读公钥来源。如果平台之后整体覆盖授权文件，公钥仍可登录，环境选项却可能消失，导致 dispatcher 无法识别 profile。平台更新与实例重建后应重新检查，不能声称本方案自动适应平台覆盖。

## 另一种可行思路，尚未在本项目实现

在支持的 OpenSSH 环境中，管理员可评估 `ExposeAuthInfo yes`：平台继续根据当前授权公钥决定是否允许登录；会话从 `SSH_USER_AUTH` 提供的本次认证信息获取公钥，再对照私有映射选 profile。未知公钥不应自动归属任何 profile；平台撤销的公钥不应因私有映射而继续获得 SSH 登录权限。不要把另一个静态授权文件放在平台授权文件之前后就认为问题解决：平台撤销后静态副本可能仍允许登录。

这需要分别实现并验证：认证信息读取与失败关闭、完整公钥匹配和重复映射检查、桌面 App Server 与 CLI、tmux 当前会话身份传递、其他平台公钥和工作密钥、平台新增与撤销、SSH 连接结束后认证文件生命周期、配置回退，以及平台重建或升级后的恢复。共享 tmux 会话可能被不同连接更新环境，不能用于隔离不同用户。

某个私有部署已做隔离公钥增删模拟和实际单用户 SSH/tmux 检查，但这不代表本仓库实现、已发布该功能、已验证所有用户私钥或真实平台更新。不得将私有公钥映射、认证文件、账号与运行日志提交至公开仓库。
